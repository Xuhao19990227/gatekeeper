# GateKeeper · AI 质量门禁工作台 —— 产品需求文档（PRD）

> 版本：v2.0 ｜ 产品名：GateKeeper（候选：ShiftLeft / 质量前哨）
> Slogan：**测试左移，每道门禁的产物让 AI 现场生成**
> 版本修订轨迹见仓库根目录 `CHANGELOG.md`

## 1. 产品定位

### 1.1 一句话定位

面向测试工程师的 **AI 质量门禁工作台**：从需求评审到代码提测，每道左移门禁的产物（评审报告/用例集/准入检查单）由智能体现场生成、可视化展示、对话迭代。

### 1.2 行业参照与差异

通用「自然语言 → 应用」的智能体生成平台已验证「AI 现场生成代码 + 可视化迭代」模式。GateKeeper 是同一种智能体生成能力在**测试左移质量流程**上的垂直实例化：

- 保留核心循环：自然语言输入 → 智能体生成代码（单文件 HTML 应用）→ 可视化网页展示 → 多轮迭代
- 垂直化差异：生成物固定为三类质量资产页面，system prompt 注入测试领域知识

### 1.3 目标用户与痛点

| 用户 | 痛点 |
|---|---|
| 测试工程师 | 测试左移喊了多年，落地卡在"产物成本"：需求评审要人肉整理问题清单、用例要在提测前写完、提测准入靠口头约定——每道门都靠手工产物撑着，忙起来门就形同虚设 |
| 测试负责人 | 门禁执行质量参差，产物无标准、无沉淀、无法复盘 |
| （叙事层）AI 编码时代的团队 | AI 大量生成代码（Copilot/Cursor 等），提测频率上升，质量保障也必须 AI 化+左移，否则测试成为瓶颈 |

### 1.3b 模块 × 质量对象 × 用户映射（不同模块的使用者不同，设计按模块拆人）

| 模块（门禁） | 管理的质量对象 | 主用户 | 判定人 / 协作方 | 状态 |
|---|---|---|---|---|
| G1 需求评审 | **需求文档质量**（可测性/完整性/无歧义） | 测试工程师 | 产品经理（材料提供方，可用报告做评审会前自检）· 测试负责人（结论判定） | ✅ MVP |
| G2 用例左移 | **测试用例质量**（覆盖度/可执行性/预期可判定） | 测试工程师 | 测试负责人（用例评审） | ✅ MVP |
| G3 提测准入 | **代码提测质量**（静态检查/冒烟就绪/风险透明） | 测试工程师 | 开发（diff 材料提供方）· 测试（准入判定：通过/打回） | ✅ MVP |
| G4 测试执行 | 缺陷与执行质量（报告规范性/回归范围） | 测试工程师 | 测试负责人（质量日报受众） | 愿景 |
| G5 发布准出 | 发布就绪质量（检查单/回滚预案） | 测试负责人 | 发布决策人 | 愿景 |
| G6 线上复盘 | 线上质量（根因/改进项/用例回流） | 测试/开发/产品 | 复盘主持人 | 愿景 |

**模块化架构声明**：门禁=模块，每模块三件套（角色包+产物骨架+判定留痕）；模块注册表=`lib/prompts.ts` 的 GATE_META，新增模块=注册一项，不改既有模块（开闭原则）；模块组织形态=左移流水线（跨门上下文流转是差异化价值），同时支持单模块独立使用（如只用 G2 生成用例）。**设计约束：PRD 与原型自 v1.0 起即按此模块化结构设计，MVP 只做三门是切片决策，不是架构边界。**

### 1.4 创始叙事

作者是 5 年测试工程师：曾作为企业内部 AI 用例生成工具的**生产环境使用者**（产物需人工修正），清楚 AI 产物哪里可信、哪里必须设人工闸口；经历过需求模糊直接开发导致的返工、提测质量差被打回的完整循环。GateKeeper 的答案：**AI 管产物生成效率，人管每道门的闸口判断**——三道人工审核的实战流程产品化。

### 1.5 用户故事（标准格式）

- 作为**测试工程师**，我想把 PRD 粘贴进来 1 分钟内拿到结构化评审报告，以便在开发动工前就暴露需求模糊点与缺失项，而不是提测后才发现。
- 作为**测试工程师**，我想让评审提取的测试点自动流转成可勾选的测试用例集并支持对话迭代，以便在等提测的窗口期完成用例设计（左移落地）。
- 作为**测试负责人**，我想每道门禁的产物可导出、可回溯（版本历史+回滚），以便门禁执行有迹可循、质量决策可复盘。

## 2. 核心流程

```
新建质量项目（输入项目名+需求材料）
   │
   ▼
Gate 1 需求评审 ──贴 PRD──→ AI 生成《需求质量评审报告》页
   │                          ├ 总体评估（可测性评分）
   │                          ├ 模糊点/歧义清单
   │                          ├ 缺失项（边界/异常流/验收标准）
   │                          └ 评审结论勾选单（人工闸口①）
   │  确认通过 → 测试点自动带入下一门
   ▼
Gate 2 用例左移 ──基于测试点──→ AI 生成《测试用例集》页
   │                          ├ 用例表（编号/模块/前置/步骤/预期/优先级）
   │                          ├ 筛选+勾选执行状态（人工闸口②）
   │                          └ 对话迭代（"补充安全类用例"→重新生成）
   ▼
Gate 3 提测准入 ──贴 diff/改动说明──→ AI 生成《提测准入检查单》页
   │                          ├ 静态检查项+风险提示
   │                          ├ 冒烟用例建议
   │                          └ 准入结论：通过/有条件通过/打回（人工闸口③）
   ▼
导出《左移质量报告》（P1 延展：三门产物汇总单页，可下载）
```

**每道门通用交互**：材料输入 → 生成（loading 态有进度文案）→ 预览 → 对话迭代 → 版本历史/回滚 → 确认过门。

**判定三态行为（闭环定义；平台侧已落地：工作台判定面板 + judgments 留痕 + 步骤条三态着色 ✓/△/✗）**：
- **通过** → 过门锁定该版本（gates 记录 versionId），门禁步骤条变绿，进入下一门
- **有条件通过** → 同"通过"，但意见栏内容随产物保留，导出存档时可见
- **打回** → 不过门、不锁版（已过门的门被打回=同步解锁）：打回意见勾选/填写于产物内 → **导出产物（自动附平台判定记录，即打回意见报告）线下流转给材料方**（G1→产品经理改 PRD；G3→开发改代码）→ 修改后重新粘贴新材料 → 走「迭代」再生成 → 再判定。**闭环哲学：产品记录判定（版本历史=判定留痕）、产出闭环工具（意见产物导出+迭代再生成），闭环动作由人承载**——"AI 管生成，人管闸口"在打回路径上同样成立；自动编排多人流转=明确不做（5.3），组织级打回度量=P2（7 节）

### 3.4 生成物内容规格（三类产物的页面骨架，system prompt 按此约束）

| 产物 | 必备区块 | 交互要求 |
|---|---|---|
| G1 评审报告 | ①总体评估（可测性 1-5 分+一句话结论）②模糊点清单（原文引用+问题+建议改写）③缺失项清单（边界/异常流/验收标准分类）④测试点提取（编号列表）⑤**无法评审项**（材料中`【图】`占位符等 AI 不可见内容→逐条列出+提示人工对照确认；system prompt 明令禁止假装评审过图片）⑥评审结论勾选单（通过/有条件通过/打回+意见栏） | 勾选、意见输入、结论高亮 |
| G2 用例集 | ①用例表：编号/模块/前置条件/步骤/预期结果/优先级(P0-P2)/状态 ②统计条（总数/P0数）③导出 CSV 按钮（含 BOM 防 Excel 乱码；用例数据流向 Excel/用例管理平台的通道） | 筛选（模块/优先级/状态）、勾选、统计联动、CSV 导出 |
| G3 准入检查单（六维深化版） | ①改动理解摘要 ②六维质量评审表：正确性/健壮性/安全性/可维护性/可观测性/兼容性，每维 0-10 评分+**必须引用具体代码行**+改进建议 ③风险提示（按严重度+建议验证方式）④冒烟用例建议（3-5条可直接执行）⑤准入结论：加权综合分（正确性/健壮性/安全×1.5）→建议映射（≥8 通过/6-7.9 有条件/<6 打回），**人可覆盖 AI 建议**+radio+意见栏。定位声明：只做语义级审查，不替代 ESLint/Sonar——**工具管规范，AI 管语义，人管判定** | 勾选、结论高亮 |

通用视觉规范（写进 system prompt）：浅色底、卡片式、圆角、系统字体、单文件、内联 CSS/JS、无外部依赖、中文界面；产物页首注明「页内勾选与填写供离线评审使用，正式判定留痕以 GateKeeper 平台判定面板为准」（产物内交互与平台判定双轨：导出后离线流转用页内勾选，平台内正式留痕用判定面板）。

## 4. 技术方案

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Next.js 15 (App Router) + React 19 + TypeScript strict + Tailwind | 单仓库单部署单元；部署平台按生成时长实测选型（无函数超时墙者优先），另挂备份链接 |
| LLM 代理 | `/api/generate` 服务端路由 | Key 只在 env；供应商可切换（env: LLM_BASE_URL / **LLM_AUTH_TOKEN** / LLM_MODEL / **LLM_FORMAT**=anthropic\|openai）；开发与生产通道独立配置 |
| 接口防护 | `x-gk-guard` 请求头校验（env: NEXT_PUBLIC_GK_GUARD） | 防公网端点被脚本直打消耗 LLM 配额；演示级防护（口令编译进前端，非真安全），生产化接真实鉴权——取舍声明 |
| 生成物 | 单文件 HTML（内联 CSS/JS，零外部依赖） | iframe `sandbox="allow-scripts allow-downloads allow-modals"` 渲染——⚠️ 生成工具内的下载/alert 必须显式放行，否则交互被沙箱静默拦截（如导出按钮点了没反应） |
| 持久化 | localStorage（主线）→ **P1-0 升级服务端 MySQL**（见 5.2，适配器换实现页面零改动） | key 设计见 4.2；客户端持久化保交付确定性+用户侧零第三方依赖；服务端 DB 为第一优先升级项 |
| 迭代机制 | 整文件重生成（上一版 HTML+修改指令一起发给 LLM） | 不做 diff 补丁（取舍） |

### 4.1 /api/generate 接口契约

```
POST /api/generate
{
  "gate": "g1" | "g2" | "g3",          // 白名单校验，非法值回 400（不静默降级）
  "materials": "PRD/测试点/diff 原文（≤4000字，服务端截断，前端超长警示）",
  "instruction": "本轮生成/迭代指令",
  "previousHtml": "上一版产物 HTML（首次生成为空；服务端 20000 字截断兜底）",
  "gateContextHtml": "上一道门已过门产物 HTML（G2/G3 携带，服务端截断至 8000 字）"
}
→ 200 { "html": "<!DOCTYPE html>..." }（无 LLM 凭据时走 Mock 模式，附 "mock": true）
→ 400 { "error": "入参校验失败原因" }
→ 403 { "error": "拒绝访问" }（防护口令不符）
→ 502 { "error": "LLM 调用失败: <摘要>" }   // 前端 toast + 重试按钮
超时：服务端 150s 熔断（函数 maxDuration=300）
稳定参数：anthropic 格式=thinking.budget_tokens 2048（thinking 与 temperature 参数不兼容，故不传 temperature）；openai 格式=temperature 0.3
```

System prompt = 通用约束（3.4 视觉规范+单文件+沙箱安全）+ 门禁角色包（G1 资深测试架构师评审需求 / G2 测试设计专家 / G3 提测准入审查员），产物骨架按 3.4 表格硬约束。

**跨门上下文传递**：G2/G3 生成时，服务端自动把上一道门的当前产物 HTML 打包进 prompt（如 G2："基于以下评审报告中的测试点设计用例"），截断至 8000 字——这是 3.2 节"测试点自动带入 Gate2"的实现机制（父页面持有产物 HTML 字符串，iframe 沙箱本身不可读）。上游门未过门时上下文缺失，前端以软门禁（确认+警示条）保证用户知情。

### 4.2 localStorage 数据结构

```
// schema v2（从属层级：账号 → 项目 → 材料/产物 → 版本）
gk_accounts        [ { username, passDigest(SHA-256), createdAt } ]        // 演示级本地账号（P1-0 升级服务端真实鉴权）
gk_session         { username, mode: "account"|"guest" }                   // 登录态；游客通道=昵称轻初始化的演化形态
gk_projects_{user} [ { id, name, createdAt,
                       materials: { g1, g2, g3 },   // 每门需求材料（PRD/diff）——从属项目、即输即存
                       gates:     { g1: verId|null, g2, g3 },              // 每门过门锁定的版本 id（=产物当前版）
                       judgments: { g1?: Judgment, ... } } ]               // 每门最近一次三态判定（verdict/note/versionId/at）
gk_versions_{pid}  [ { id, gate, instruction, html, createdAt } ]          // 版本链：按 gate 分组即"产物 1→N 版本"

// 从属关系声明：账号 1→N 项目；项目 1→3 需求材料 + 1→3 门禁产物（每门锁定一版）；产物 1→N 版本
// 判定与锁状态同步：通过/有条件通过→锁定当前版；打回→解锁（判定三态与 gates 记录强一致）
// 本结构=P1-0 数据库表设计蓝图（accounts 表 + projects 表含 materials JSON 列 + versions 表；
// 页面只经 lib/storage.ts 适配器读写；DB 侧从属链=accounts→projects→versions 外键，versions 不冗余 owner 列）
// 写入失败显性化：存储层写操作返回布尔，失败时 UI 明确提示「未保存成功」（4.5 可靠性）
```

### 4.3 文件与存储策略：无 OSS 架构（架构取舍说明）

本产品全链路无二进制文件存储需求，**不需要对象存储（OSS）**：
- 材料输入=文本（主线粘贴；P1 支持 .txt/.md 上传=浏览器 FileReader 本地读取，文件本体不上服务器）
- 生成物=HTML 字符串，存 localStorage；导出=浏览器 Blob 本地下载
- 分享链接（P0 扩展）=HTML 压缩编码进 URL hash（# 后内容不发送至服务器），零基础设施
- 服务端无状态，只转发文本给 LLM → 部署零存储依赖
- **需要 OSS 的触发条件（列 P2 扩展规划）**：跨设备同步／团队资产库／生成物含图片附件／大文件

### 4.4 示例 PRD（内置，故意埋缺陷供 Gate1 检出——演示效果的关键设计）

> **需求：优惠券领取功能**
> 用户在活动页可以领取优惠券，页面交互见【图1：领券页原型图（文字演示略）】。领券成功后在"我的优惠券"中可以看到。优惠券有使用门槛和有效期。活动很火爆，要保证用户体验，页面加载要快。每个用户都可以领取优惠券，领了就能用。如果出现问题联系运营同学处理。

预埋缺陷（设计笔记，不出现在产品里）：①"加载要快"无量化标准（模糊）②未定义每人限领几张（边界缺失）③未定义库存不足/并发领取的处理（异常流缺失）④未定义过期券展示与使用规则（边界缺失）⑤"联系运营处理"无系统兜底方案（异常流缺失）⑥无验收标准 ⑦图1 为图片占位，AI 无法评审→应列入"无法评审项"提示人工确认（**此命中=产品边界自觉，system prompt 明令禁止假装评审图片**）。——Gate1 报告应至少命中 4 条（含⑦），以此 PRD 作为生成质量的验收基准。

### 4.5 非功能需求（汇总）

| 类别 | 要求 |
|---|---|
| 性能 | 单次生成 P95 ≤ 60s（实测参考：小型产物秒级、报告级产物约 1 分钟）+loading 进度文案缓解等待焦虑；LLM 调用 150s 超时熔断；首屏加载 ≤ 2s |
| 输入约束 | 材料 ≤ 4000 字（前端超长警示+服务端截断）；跨门上下文 ≤ 8000 字截断；迭代基线 ≤ 20000 字截断兜底 |
| 兼容性 | 桌面端 Chrome/Edge 最新两个大版本；移动端不适配（取舍声明，见 5.3）；crypto.subtle 依赖安全上下文（部署须 HTTPS 域名） |
| 安全 | LLM token 仅存服务端 env；接口防护口令（4 节）；iframe sandbox 权限白名单（allow-scripts/downloads/modals，不给 allow-same-origin）；无真实鉴权=演示级声明（3.5）；生成代码不出沙箱执行 |
| 可靠性 | LLM 失败→toast+重试按钮不白屏；localStorage 写入异常→明确提示"未保存成功"（存储层返回布尔，调用方负责提示） |

## 5. 需求优先级与范围

### 5.1 必做（MVP）
P0-1 首页项目列表+新建 ｜ P0-2 工作台三门流程（材料→生成→预览→迭代）｜ P0-3 三套门禁 system prompt+示例 PRD ｜ P0-4 localStorage 持久化 ｜ P0-5 版本历史+回滚（延展能力①）｜ P0-6 产物导出 HTML（延展能力②）｜ P0-7 部署上线（主+备双链接）

### 5.2 时间富余才做（P1-0 为第一优先升级项）

**P1-0 服务端数据库 + 真实注册登录**（触发条件=主线三门 E2E 验收通过）：
- 平台联动选型：Zeabur 部署→**Zeabur MySQL**（同区一键开通/支付宝可付）；Vercel 部署→Neon Postgres 免费层（**服务端连接模式**：用户浏览器只访问应用域名，DB 连接在服务端，用户侧可达性与 DB 厂商解耦）
- MySQL 化注意：JSONB→JSON 类型；html 列用 MEDIUMTEXT（单份产物 30-60KB，TEXT 的 64KB 上限不留余量）；驱动 mysql2/promise + 连接池 + prepared statement（不手拼 SQL）
- 实现方式：`lib/storage.ts` 适配器换实现 → 新增 /api/projects、/api/versions CRUD 路由 + 服务端 DB；页面代码零改动（适配器设计的兑现）
- 注册登录升级：登录/注册页面与游客通道**已实现**（本地 SHA-256 鉴权适配版）——P1-0 仅将鉴权与存储实现换为服务端 DB（密码服务端哈希+会话 cookie），页面代码保留（适配器模式第二次兑现）
- 数据迁移：localStorage 已有项目一次性导入或弃用（demo 数据无迁移价值，弃用+文档注明）

P1-1 导出《左移质量报告》汇总页 ｜ P1-2 加载示例项目一键体验（**已实现**：首页「加载示例项目」+工作台 demo 预填+同名去重）｜ P1-3 材料文件上传 .txt/.md（FileReader 本地读取文本）｜ P1-4 **dogfooding 演示**：把本 PRD 摘要喂给 Gate1，生成《对本产品自身需求的评审报告》（"用产品评审造出它的需求文档"，自证真实可用）｜ P1-5 UI 打磨（动效/深色模式）｜ P1-6 判定留痕升级为历史数组（judgments 1→N，DB 化时天然获得）｜ P1-7 版本记录材料快照（追溯"该版本由什么材料生成"）

### 5.3 明确不做（取舍说明）
真实服务端鉴权（本地账号=演示级，见 3.5；生产化接 Supabase/Clerk 列扩展规划）／图片多模态理解（生产 LLM 通道为纯文本，视觉模型接入列 P2；MVP 以"无法评审项+人工闸口"显式处理，不假装能看图）／CI·Git 集成自动触发门禁（扩展规划：接 webhook）／多人协作与评审流转／生成物 PDF 导出／移动端适配／真实缺陷系统对接。
**诚实边界声明**：MVP 是独立工作台，"门禁"指产物生成与人工闸口判断（软门禁=干预+知情，不强制拦截），不拦截真实流水线——名实相符，不 over-promise。

### 5.4 风险 Top3 与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| LLM 生成产物质量不稳（区块缺失/交互失效） | 高 | 3.4 骨架硬约束+低温度+示例 PRD 实测前置（G1 命中≥4/7 才继续）+重新生成按钮兜底 |
| 生产通道 LLM 连通失败（跨境/限流/欠费） | 中 | env 双通道可切（OpenAI 兼容/Anthropic 兼容）；空壳部署阶段即从线上环境实测发一条真请求 |
| 时间超支（主线做不完） | 中 | **降级阶梯**：P1 全砍 → 砍 Gate3（保 G1/G2 两门闭环仍成立）→ 砍版本历史保导出；**部署与文档永不砍** |

## 7. 扩展规划

- **产品愿景**：**中小项目团队的全流程质量门禁平台**——门禁地图覆盖完整开发流程：G0 需求澄清门（《澄清问题清单》）→ **G1 需求评审门 ✅MVP** → **G2 用例左移门 ✅MVP** → **G3 提测准入门 ✅MVP** → G4 测试执行门（缺陷报告质量核查/质量日报/回归范围建议）→ G5 发布准出门（发布检查单/回滚预案核查）→ G6 线上复盘门（故障复盘报告/线上问题转回归用例）。**定位叙事「从门禁到质量管理：点→线→面」**：MVP=三道左移门禁（点，GateKeeper=守门人）→ P1 接 CI 串进研发流水线（线）→ P2 组织级质量资产与度量（面）；当前核心机制是纯门禁（每道门有判定：通过/有条件通过/打回+过门留痕），质量管理平台是演进方向不是当前承诺——与「诚实边界声明」互为表里。**MVP 切片=G1-G3 左移三门**，切片依据：①作者主场（五年测试痛点故事全在此段）②AI 价值密度最高（文本进文本出；G4-G6 依赖缺陷/监控系统的结构化数据集成，属 CI 集成期工作）③演示材料已备（预埋 7 缺陷示例 PRD）④**愿景与切片的缝=门禁角色包（lib/prompts.ts）：每扩一道门=一个角色常量+一个产物骨架，成本线性增长**

- **P0**：《左移质量报告》一键导出／产物分享链接（团队资产化）
- **P1**：Git/CI 集成（提测 PR 自动触发 Gate3）／**G3 材料形态升级**（.diff/.patch 文件上传、整文件审查、历史判定回查=上次打回问题是否复发的回归检查）／产物模板自定义（企业规范注入）／评审流转与多人协作
- **P2（生态协同）**：与 AI 编码/应用生成平台配对——上游平台生成代码时，本平台自动生成对应的门禁产物（需求→用例→准入全自动左移闭环）；**多模态需求评审**（接视觉模型直接读原型图/流程图，覆盖图文混排 PRD，消灭"无法评审项"）；**代码质量双引擎**（摄入 ESLint/SonarQube 扫描报告+覆盖率数据作为 G3 材料，AI 做语义层审查与汇总裁定——"工具管规范，AI 管语义，人管判定"的完全体）／代码库 RAG（跨文件影响分析）；**敏感材料合规通道**（私有化模型部署/脱敏网关——企业 PRD 与代码 diff 不出域，金融/外包内网场景的入场券）；**生态边界=集成而不做**：上游工具（AI 生成平台/PM 工具）产出需求/原型/代码，GateKeeper 为一切生成物守门——完整 PRD 撰写与原型绘制不做（那是上游赛道），需求文档生成能力以 G1「建议改写」列为微形态、随 G0 澄清门深化；组织级质量资产沉淀与度量
- **目标用户分层**：核心=无工具开发资源的中小团队/驻场测试工程师（门禁产物手工成本半天→1 分钟）+单人 QA（产物即话语权）+测试负责人（DB 版后有迹可循可度量）；路线解锁=PM 评审前自检/AI 编码团队（生态配对）/企业质量部门（规范注入+度量）；明确不适合=已有成熟 DevOps 门禁的大厂（切入点为插件非替代）、审计级签核场景、移动端；**产物单文件 HTML 导出的设计依据=金融/外包内网屏蔽外链，文件形态双击即用**（用户网络现实倒推产物形态）
